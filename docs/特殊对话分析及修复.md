# 特殊对话（会話変換）分析与修复

本文档汇总 first.dll 中四种"特殊对话/语言转换"模式的机制分析、数据地址、汉化版适配现状与修复方案。

- 分析对象：原版 `input\first.dll`（偏移均为**文件偏移**）
- 结论速览：**四种模式中，ひんたぼ/グロンギ/にょ 均为"数据表驱动"，汉化管线已覆盖（故可用）；重力語为"逻辑驱动"无表可翻，在 GBK 环境下仅剩 ASCII 小写——已用"逐字映射表"修复（原版会变的 SJIS 字符凡在 GBK 存在的逐字复刻，对话与菜单窗口两路径同时生效，方案见 §6）**

---

## 1. 四种模式与出处

| 原名 | 译名 | 出处 | 表现 |
|---|---|---|---|
| ひんたぼ語 | Hintabo语 | 游戏《北野武的挑战状》中虚构岛国的语言 | 假名沿五十音顺序后移 |
| グロンギ語 | 古朗基语 | 《假面骑士空我》古朗基族的语言 | 按音组归并映射到片假名 |
| 重力語 | 重力语 | 《仙境传说》(RO) 日文编码 BUG（Gravity = 开发商名） | 命中 SJIS 尾字节 `0x41–5A`（→+0x20）的字符换成对应结果字，导致部分假名和汉字错位、字母小写 |
| にょ | 喵语 | 《Di Gi Charat》主角数码子的口癖（句尾加"にょ"） | 特定语尾+终结符替换为"にょ"（标点保留；中文可用"喵"） |

- 译名 = 汉化版配置窗/菜单中实际显示的名字（配置窗：Hintabo语 / 古朗基语 / 重力语 / 喵语；菜单项：古朗基语转换 / 重力语转换）

## 2. 架构与触发

- **配置窗复选框**（DFM 字段）：`gurongicbox` / `gravitycbox` / `nyocbox` / `hintabocbox`
- **INI 键**（HKCU 下 SSP 配置）：`gurongigateflag` / `gravitygateflag` / `nyogateflag` / `hintabogateflag`
  - 对应全局字节：`0x4ADCF0`(古朗基) / `0x4ADCF4`(重力) / `0x4ADCF8`(にょ) / `0x4ADCFC`(ひんたぼ)
- **菜单命令**：`jtogg`（古朗基语转换）/ `jtogv`（重力语转换）；另有 `compjapan`（CompJapan 功能）
- **应用顺序**（依次叠加，前一个输出喂给后一个）：**ひんたぼ → にょ → グロンギ → 重力語**
  - 入口函数 `0x4708DC`（内部按开关逐个调用下方函数；旧文档误记为 0x4708F0）
- **数据记录格式**（Delphi 短字符串常量）：
  `[refcount:4 = FFFFFFFF][len:4 字节长][文字][补齐到 4 字节]`
  - CSV 行格式：`偏移,字节长,code,文本`，其中偏移/长度均指**文字区**（refcount+len 之前 8 字节）

## 3. 各模式机制

### 3.1 ひんたぼ語（移位链）｜函数 `0x41BBE8`

- **数据表：`0x1BB48 – 0x1BF12`（81 条单字记录）**
- **规则：每个假名替换为数据表中的下一条记录**（实现：`cmp 本条; append 下一条`）
- 数据序列（= 映射链）：
  `あ→い→う→え→お→か→き→く→け→こ→さ→し→す→せ→そ→た→ち→つ→て→と→な→に→ぬ→ね→の→は→ひ→ふ→へ→ほ→ま→み→む→め→も→や→ゆ→よ→ら→り→る→れ→ろ→わ→を→ん→っ→ゃ→ゅ→ょ→ぁ→ぃ→ぅ→ぇ→ぉ→ー→(循环回あ)`
  浊音/半浊音为侧链：`が→ぎ→ぐ→げ→ご→ざ→じ→ず→ぜ→ぞ→だ→ぢ→づ→で→ど→ば→び→ぶ→べ→…（表尾 ぽ/ぼ/ぱ/ぴ/ぷ/ぺ 顺序以数据表为准）`
- 非假名字符（汉字/标点/ASCII）原样保留

### 3.2 にょ（语尾替换 + 终结符占位机制）｜函数 `0x419520`

- **不是"把语尾全替换成にょ"**；实际是 **12 条规则**（11 条语尾替换 + 1 条"终结符前插入"），每条规则**只在后面紧跟"终结符"时命中**，且**终结符本身保持不动**：
  - 语尾规则形态：`X + T → Y + T`（T = 终结符）
  - 第 12 条为**插入规则**（查找串为空）：`T → にょ + T`，即**在每个终结符前加にょ**（"句尾加にょ"的主来源）
- **终结符 T（10 个）**：`。 ‥ … ・・ （ ー ？ ！ ～ っ`
- **占位符 M（10 个）**：`0x01 – 0x0A`（与上面终结符按顺序一一对应）
- **实现机制（三段）**：
  1. **A 阶段**：包装函数 `0x419134` 为每条规则、每个终结符拼出一对"查找/替换"，再调核心 `0x418DB0`：
     - 查找 = `X + T`；替换 = `Y + M`（终结符被临时换成占位符）
  2. **C 阶段**：函数 `0x417B6C` 调用 10 次，把占位符 `0x01–0x0A` 还原为对应终结符
     - 净效果 = 只把 X 换成 Y、终结符原样保留；占位符用于防止"新换出的字被后续规则连锁替换"
  3. **B 阶段**：函数 `0x417C90` 调用 3 次，消重清理 `ぅにょ / にょーにょ / にょにょ → にょ`
- **跳过保护**：命中点前面若是占位符（0x01–0x0A）或符号 `。‥… ・・・（ー？！っ` 则跳过
- **12 条规则**（11 条语尾替换 + 第 12 条插入规则；表内 #12）：

  | # | X（查找） | Y（替换） |
  |---|---|---|
  | 1 | だよね | ですにょ |
  | 2 | のだぁ | のにょ |
  | 3 | よね | にょ |
  | 4 | ねぇ | にょ |
  | 5 | なぁ | にょ |
  | 6 | だぁ | にょ |
  | 7 | いの | いのかにょ |
  | 8 | な | にょ |
  | 9 | ね | にょ |
  | 10 | よ | にょ |
  | 11 | の | にょ |
  | 12 | （空/无） | にょ ｜ 插入规则：`T → にょ+T` |

- **"句号前面会加'にょ'"的完整解释（两种来源）**：
  1. **语尾规则**：如 `ね。` 命中规则 9 → `にょ + 占位符01` → C 阶段还原 → `にょ。`（不新增，只是替换）
  2. **插入规则（第 12 条）**：不含上述语尾的句子也会命中 → `普通。` → `普通にょ。`（每个终结符前插入にょ）
     - 实机验证（独立宿主）：`普通。`→`普通喵。`、`啊。哦。`→`喵。哦喵。`
  3. B 阶段 `にょにょ → にょ` 等消重用于**防止重复转换叠加**（插入规则在二次转换时会再插一次，靠消重还原）
- **数据区（文件偏移，均为文字区起始）**：
  - 规则串（X/Y）：`ですにょ`@0x18CBC、`だよね`@0x18CD0、`のにょ`@0x18CE0、`のだぁ`@0x18CF0、`にょ`@0x18D00、`よね`@0x18D10、`ねぇ`@0x18D20、`なぁ`@0x18D30、`だぁ`@0x18D40、`いのかにょ`@0x18D50、`いの`@0x18D64、`な`@0x18D74、`ね`@0x18D80、`よ`@0x18D8C、`の`@0x18D98
  - 终结符/占位符对（C 阶段还原用）：`。`+`01`@0x18DA4、`‥`+`02`@0x18DBC、`…`+`03`@0x18DD4、`・・`+`04`@0x18DEC、`（`+`05`@0x18E08、`ー`+`06`@0x18E20、`？`+`07`@0x18E38、`！`+`08`@0x18E50、`～`+`09`@0x18E68、`っ`+`0A`@0x18E80
  - 拼接常量区（A 阶段拼 `X+T` / `Y+M` 用，同一套对的另一份）：0x18834–0x1891C
  - B 阶段消重串：`ぅにょ`@0x18E98、`にょーにょ`@0x18EA8、`にょにょ`@0x18EBC
  - 第 12 条插入规则：X=空（调用参数 edx=0，位于 0x419520 内 0x4196BF 附近）、Y=`にょ`@0x18D00

### 3.4 重力語（逻辑管线，无数据表）｜函数 `0x418CD4`

- **无任何字符串表** → 翻译管线无法覆盖；效果由"字节级处理"产生
- 完整管线（对话路径，五步）：
  1. `0x417C90`：把原文 `%` 换成 0x01 保护（跳过 `[ ]` 指令区）——因为解码步会把 `%`+2字符当转义，字面 `%` 必须先藏后还
  2. `0x417048`（**转义**）：逐字节扫描；`IsDBCSLeadByte`（按系统代码页，CN 机=CP936）判双字节对：
     - 尾字节是"大写字母"（`IsCharUpper`）→ 输出 `%` + hex(前导) + **尾字节原样**
     - 否则 → `%` + hex(前导) + `%` + hex(尾字节)
     - 单字节原样
  3. `0x408358`：`user32!CharLowerBuffA` 整串小写——把第 2 步**故意裸露的尾字节** A-Z 压低
  4. `0x4171A0`（**解码**）：`%XX` → 字节（大小写不敏感）
  5. `0x417C90`（参数对调）：0x01 还原为 `%`
- **净效果** = 双字节字符的尾字节落在 `0x41–0x5A` 时 **+0x20**（同行内换字），外加 ASCII 小写：
  - 片假名（SJIS `83 41~83 96`）尾字节大量落在该区 → 变另一个片假名：`リンゴ`→`リンピ`（ゴ=8353→8373=ピ）、`ガード`→`ヌード`（ガ=834B→836B=ヌ）
  - **GBK 汉字尾字节为 A1–FE，永不命中该区 → 中文版形同失效（只剩 ASCII 小写）**；仅极少数二级汉字（尾字节 0x41–5A）会中招
- 菜单「重力语转换窗口」（`Tjtogvform.editChange` @0x46FBC0）= **同样的核心三步**（转义→小写→解码），但没有 1/5 的 `%` 保护 → 窗口输入含 `%` 时被解码吃掉（实测 `%41`→`A`、`%`→NUL）
- **两处原版遗留隐患**：① 方括号区跳过的只是 1/5 步，转义/解码扫全串 → 指令参数里的 `%xx` 照样被吃（URL `%20`→空格）；② 窗口无 `%` 保护
- **不做**：字节边界错位型乱码（如 `取引を要請する`→`去来要請`，属 SJIS 被按其它编码误读，与本功能无关）

## 4. 汉化版现状（已验证）

### 4.1 三个表驱动模式为什么能用
翻译管线（extract.csv → translated.csv → patch_dll.py）**覆盖了替换表区**，把表写成了 GBK：

| 表 | 原版 | 中文版 |
|---|---|---|
| グロンギ 0x1A948 | `82 A0`(SJIS あ) | `A4 A2`(**GBK あ**) |
| ひんたぼ 0x1BB50 | `82 A0`(SJIS あ) | `A4 A2`(**GBK あ**) |
| にょ 0x18CBC | `ですにょ` | `喵~` |
| にょ 0x18CD0 | `だよね` | `呢` |
| にょ 0x18CE0 | `のにょ` | `的喵` |
| にょ 0x18CF0 | `のだぁ` | `的呢` |

- 输入文本同为 GBK → 与表字节一致 → 命中替换 → 正常工作
- にょ 的表条目已大部分翻译为中文语尾（呢 / 的喵 / 喵~ …）；仍有个别单字规则未翻译、以及一对"哟/っ"不同步，详见 §5 末尾

### 4.2 重力语为什么失效
- 无表可翻（纯逻辑）；且命中条件（尾字节 0x41–0x5A 大写区）在 GBK 文本上基本不存在（GBK 汉字尾字节 A1–FE）→ 只剩 ASCII 小写
- 中文版已改为"逐字映射表"驱动的 GBK 变换桩（原版会变的 SJIS 字符凡在 GBK 存在的逐字复刻），对话与菜单窗口两条路径一起生效，详见 §6（已实施）

## 8. 打字游戏与四模式的冲突（已修复）

### 8.1 现象与原因

- **现象**：开着任一模式玩打字游戏时，出现"喵"的位置**无论照原文打还是照显示打都不对**。
- **输入链路**（问题根源）：

  ```
  输入框(你打的字) → 拼成 \![raise,OnTypinggameInput,你的字] → 经 SSTP 发给 SSP
                   → SSP 当作"脚本"送翻译 → 落到 DLL 的 OnTranslate → ConvertAll(你的字)
                   → 事件回到 DLL，判定却按"原文 vs 原文"比较 → 永远差一层转换
  ```

- 题面显示也走同一条翻译链（显示 = C(题面)）。
- 判定位置：`OnTypinggameInput` 处理（0x474069 附近）按"原文 vs 原文"精确比较；另注：C 不是幂等的（如 `呢。`→`喵~。`→`喵~喵。`），所以"打显示文"同样不过。

### 8.2 修复总思路：不是"关掉翻译"，而是"在转换函数里做手术"

所有转换最终都调用同一个函数：`0x47239D: call 0x4708DC`（ConvertAll；约定 **EAX=待翻译文本、EDX=输出变量地址**）。把这句 call 改跳到自己写的桩（`.cave+0x3A10`），桩内三分支：

```
游戏进行中？ [0x4ADCDC] == 0 → 照常 ConvertAll（与原来一模一样）
进行中：
  ├─ 文本含 \![raise,OnTypinggameInput, → 原样复制给输出（你打的字整段放行）
  ├─ 文本含当前"要打文本" P=[0x4B29F8] → out = C(前缀) + P + C(后缀)
  └─ 其他（提示语、结算语…）           → 照常 ConvertAll（模式风味保留）
```

### 8.3 两个"识别点"从哪来

- **游戏进行中**：`[0x4ADCDC]` 是游戏自己的状态字节（进游戏置 1、退出置 0；倒计时逻辑也用它）→ 退出自动恢复，无需额外挂钩。
- **玩家输入脚本**：打字框拼串模板是 DLL 内常量 `\![raise,OnTypinggameInput,`（0x46EBFC）；在文本里搜该特征串即识别，整段放行（连 `\![...]` 语法一起保持原样，最稳）。
- **要打文本**：游戏每轮把"当前该打的字"存进全局 `[0x4B29F8]`（判定时用它比较），显示消息里原样嵌入 → 在待翻译文本里找到它、只保护该子串。
- 无论 SSP 送整段脚本还是只送提取后的文本（`\![...]` 内文本），两种行为都被覆盖。

### 8.4 核心：字节级子串手术

DLL 字符串为 ANSI（中文 CP936）单字节串，全程按**字节**操作，多字节汉字不会切坏：

1. **查找**：桩内联字节查找循环（外层走位置、内层逐字节比较），返回 P 在文本中的字节偏移 `o`；
2. **前缀**：借用 DLL 自带工具 `0x4187B4`（`out := Copy(s, 1, n)`）取前 `o` 字节；
3. **后缀**：整串复制 → `SetLength`(0x404174) 触发**写时复制**得到独占缓冲 → `rep movsb` 把 P 挤出（尾部左移）→ `SetLength` 收缩；
4. **转换**：对前缀、后缀各调一次原版 ConvertAll（空串跳过，防 nil）；
5. **拼回**：`out := C(前缀)`，再用 `LStrCat` 拼原文 P，再拼 C(后缀)（0x403C14 / 0x403E48）；
6. **返回**：还原栈帧与寄存器后 `ret` 回到原 call 的下一条指令——对原逻辑完全透明。

因前缀/后缀是**分开**转换再拼回的，转换规则永远不会"看到" P，P 天然免疫。

### 8.5 位置无关性与透明性

- DLL 可能被重定位（不一定加载在 0x400000）。桩内所有 DLL 内部地址都用**运行时基址差**修正：
  `call $+5; pop eax; sub eax, 链接期地址` → 得 delta 存 `[ebp-0x2C]`，之后 `delta + 链接地址` = 运行时真实地址；跳转/调用全部相对位移。
- 进入/退出完整保存 EBX/ESI/EDI/EBP；只动 EAX/ECX/EDX（调用方视为易失），符合 Delphi 寄存器约定。
- 桩 ≤ 0x1F0 字节（构建断言保证，止于下一桩 0x3C00 之前）。

## 6. 重力语中文化（已实施）

### 6.1 方案结论（替代早期草案）

早期"方案 A（GBK↔SJIS 转码包装）"会破坏中文台词、"方案 B（手工维护 CSV 替换表）"只覆盖假名——均未采用。实际采用**代码级替换核心"转义"一步 + 构建时代码生成的逐字映射表**：

- 在对话管线（`0x418D21`）与菜单窗口（`0x46FC03`）两处把 `call 0x417048` 改道到新桩（`.cave+0x3C00`）；
  **不动函数本体**——它还兼任百度搜索的 URL 百分号编码器（调用点 `0x476548` 保持原样）
- 桩内实现 GBK 变换（一次扫描 + 3×len 预分配 + 收尾 SetLength；输出全小写 `%xx` 转义，
  交后续原有"小写+解码"两步还原，对其严格幂等/可逆、不依赖 `CharLowerBuffA` 的 DBCS 行为）：
  1. ASCII `A-Z` → `a-z`
  2. **表驱动逐字复刻**（`cave+0x3E00`，1044 条 = 假名 32 + 汉字 946 + 符号 66；329 条因不在 GBK 排除）：把"原版会变的 SJIS 字符（双字节、尾字节 `0x41–0x5A` → `+0x20`）"中**凡在 GBK 也存在的逐字映射**成表——命中则换成表中结果，未命中（SJIS 不存在 / 不受影响 / 不在 GBK）一律原样
  3. `[ ]` 区逐字节原样（脚本指令安全；**并修复原版"方括号内 %xx 被解码吃掉"的洞**）
  4. `%` → `%25`（保住环境变量标签 `%month`/`%*` 与字面百分号；**窗口路径同样保留**，修掉 `%41`→`A` 怪癖）
- 依据：UKADOC（さくらスクリプト）——`%` 是环境变量埋入标签前缀、字面 `%` 写作 `\%`；
  `[ ]` 为标签参数区；first.dll 自身就在 Todo/Notify 文本中使用 `%*` 标签

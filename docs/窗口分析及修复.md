# first.dll 窗口分析与修复

本文汇总 first.dll 自带窗口（DFM 窗体）的清单与用途、字体归属，以及窗口文本编码、
高分屏缩放两类修复；拖动相关见 4.1，退出崩溃修复见第 8 节。

---

## 1. 窗口清单与用途

DLL 通过 DFM 建 19 个窗体；可在设置窗（Tfirstconfigform）的勾选框里开关的共 6 个：
模拟时钟 + 5 项文字信息。其余为菜单/工具/游戏窗。

|---|---|---|---|

`等线` / `楷体` 等短名。

## 3. 窗口文本编码修复（DFM Font.Charset → GB2312_CHARSET）

DLL 是 ANSI 程序，DFM 字符串按字节交给系统，按渲染路径分两种解释：

- **TLabel 等 VCL 自绘文字**：GDI 的 ANSI 文本函数按**当前字体 charset 对应的代码页**转换字节；
- **窗口控件（TButton / TCheckBox / TTabSheet / TTreeView / TEdit 等，有 HWND）**：文案走窗口消息，
  系统按 **ACP**（本机 = 936/GBK）转换。

原版把 18/20 个窗体的 `Font.Charset` 设为 `SHIFTJIS_CHARSET`（CP932），所以这些窗体里的
TLabel 文案必须是 Shift-JIS——`translated.csv` 中原先有 12 条 rsrc 行（Tfirstconfigform /
Tnotifyform 的全部 label：うるさい ／ 黙 ／ 月 ／ 日／毎週 ／ 時 ／ 分 ／ メッセージ ／
日時 ／ 実行ファイル ／ 年 ／ 曜日 ／ 喋る頻度(&A)）靠 `SHIFTJIS_OFFSETS` 特判保持 SJIS，
译文只能用 SJIS 允许的字符。唯一未设 charset 的 Tversionforms，其 label（beveltitlelabel）
本来就按 ACP 走，GBK 无碍。

现由 `patch_dll.py` 的 `patch_dfm_charset()` 把这两个窗体的 `Font.Charset` 改为
`GB2312_CHARSET`（值编码 `07 10 "SHIFTJIS_CHARSET"` → `07 0E "GB2312_CHARSET"`；
值之后到本窗体数据块末尾的内容整体左移 2 字节、块尾补 0，资源大小与后续资源位置不变；
**必须在文本翻译写入之后执行**，翻译随区块一起平移、DFM 结构保持自洽）。改后这两个
窗体的 label 文案按 CP936 解释，随大流使用 GBK；`SHIFTJIS_OFFSETS` 已清空，那 12 行
译文可改用任意 GBK 汉字。其余 16 个窗体保持 `SHIFTJIS_CHARSET` 不变（其中没有
需要翻译的 label 文案）。

## 4. 高分屏缩放（load/request 导出包装 + UNAWARE_GDISCALED）

**问题**：所有 DFM 窗体 `Scaled = False`、`PixelsPerInch = 96`；SSP 是 DPI 感知进程，
系统不做位图拉伸，于是 DLL 自建窗口在 150%/200% 屏上仍然只有 96dpi 大小。

**方案（现行）**：不动 API 导入/跳板，把 DLL 的 `load` / `request` 两个导出入口改指向
`.cave` 包装桩：调用真实函数**之前**把当前线程 DPI 上下文切到
`UNAWARE_GDISCALED(-5)`，**之后**还原。于是装载/请求期间创建的窗口（含窗口控件与
FormPaint 自绘文字）全部被系统按屏幕缩放且清晰（GDI 缩放）；请求之外 SSP 自己的界面
不受影响。

实现要点（`patch_dpi_wrap()`）：

- 只改 PE 导出表两个 RVA（`load` / `request` → `.cave+0x1F7C` / `.cave+0x170`）；
- 桩为位置无关代码，全部状态在栈上（可重入）；`SetThreadDpiAwarenessContext` 指针惰性解析
  （`GetModuleHandleA("user32.dll")` + `GetProcAddress`，IAT 槽 0x4B31E4 / 0x4B31E0），
  数据（PSET 指针 + 字符串）放 `.cave+0xB0`；
- 导出是「调用方清栈」（函数末尾裸 `ret`），桩也以裸 `ret` 返回；调用真实函数后由桩
  `add esp,8` 清掉自压实参副本；
- 总开关 `DPI_WRAP_ENABLE`。

**互斥方案**：DFM `Scaled=False → True`（`patch_dfm_scaled()`，由 `DFM_SCALED_ENABLE`
控制，默认关闭）。VCL 会按屏幕 DPI 放大一次，与导出包装叠加会双重放大；且该方案覆盖不了
自绘文字。

### 4.1 拖动相关的 SendMessage 包装

信息窗拖动 = 窗体 `FormMouseMove` 事件（按住左键移动）里
`ReleaseCapture()` + `SendMessage(WM_SYSCOMMAND, SC_DRAGMOVE=0xF012, MAKELPARAM(X,Y))`。
共 6 处（0x46326D / 0x46755E / 0x468C56 / 0x46D615 / 0x46EC75 / 0x4704DE，对应 6 个
窗体类）。`patch_dpi_drag()` 把这 6 个 `SendMessageA` 调用改指向 `.cave+0x2000` 的包装桩：
调用期间（含整个拖动模态循环）线程置 GDISCALED、返回后还原，形参 4 个 dword、`ret 16`。

### 4.2 .cave 布局（含高分屏部分）

```
0x0170  request 包装桩（临时模式）        0x1F7C  load 包装桩（临时模式）
0x00B0  高分屏数据：PSET / "user32.dll" / "SetThreadDpiAwarenessContext"
0x2000  拖动包装桩（SC_DRAGMOVE 的 SendMessageA）
0x2200  系统字体初始化包装桩（见 4.3）
0x226A  退出修复：收尾例程        0x2360  退出修复：枚举回调
0x2400  退出修复：存根            0x2640  退出修复：归还桩（V7）
0x2700  退出修复：入口跳板（V7；见第 8 节）
```
节大小 **0x2800**。其余偏移见
《菜单逻辑分析及补丁.md》第 5 节。

### 4.3 系统字体初始化包装（Todo/Notify 状态栏提示字缩放修复）

**问题**：Todo / Notify 窗口底部状态栏提示文字（"信息"）在缩放后过大。

**根因**：状态栏字体不是窗体字体，而是**系统消息字体**（`Microsoft YaHei UI`），由
`SystemParametersInfo(SPI_GETNONCLIENTMETRICS)` 在**线程 DPI 感知时**取得（144dpi 规格
→ h=-18），放进被系统虚拟化的窗口里又放大一次。字体初始化函数 0x44E024 只在
0x44D946 / 0x44EEED 两处被调用（无间接引用）。

**方案（`patch_dpi_sysfont()`）**：把这两处调用改指向 `.cave+0x2200` 包装桩：调用期间线程
置 `UNAWARE_GDISCALED` → 取到 96dpi 规格（h=-12），恢复后原样返回；与窗口里其它控件一致。

**已放弃**：给窗口类补 `CS_HREDRAW`（修状态栏 resize 重影，见第 7 节）。

## 6. 透明窗命中判定修复（最终方案：窗口高度减半 + misaki 整层填充）

**现象**：DPI 缩放后，文字信息窗（Tcpuloadform）只有部分文字像素能点/能拖，模拟时钟
（Tanalogclockform）几乎全盘不可点。

**根因**：这些窗口是 `WS_EX_LAYERED`（`UpdateLayeredWindow` 逐像素 alpha）且被 DPI 虚拟化
（物理 222×192 = 虚拟 148×128×1.5）——**系统只缩放显示，命中检测仍按图层像素 alpha**
（alpha==0 穿透），而图层里只有字形像素 alpha>0。
图层位图由 **misaki.dll** 管理（first.dll 只是调用方）：每帧绘制前 first.dll 调
`allclear(图层句柄, 0)`，由 misaki 把整幅位图逐行清零。

**修复（两个补丁，均极小）**：

1. **misaki.dll**：把 allclear 的 32bpp/24bpp 两处行清零调用（0x4622D4 / 0x462333 → 清零
   助手 0x406C38）改指向代码段尾部零填充里的位置无关小桩。桩按循环现成寄存器识别图层
   （高 = EDI+ESI；行字节 = 宽×4 或 宽×3）：

   - **文字信息窗（148 宽：592/444 行字节）**：整层填 `0x01`（alpha=1/255，肉眼不可见但可命中）；
   - **模拟时钟（64 宽：256/192 行字节）**：整体填 `0x01`（整窗可拖）；
   - **其余图层（倒计时等）**：原样清零，不做处理。

   只改 allclear 的两处调用，misaki 其它零填充（字符串/缓冲等）不受影响。

2. **first.dll**：Tcpuloadform 布局里两处写死高度 `mov edx,0x80; call SetClientHeight`
   改成 `0x40`（文件偏移 0x67D1A / 0x67EC0，两处都要改——另一处会覆盖）→ 信息窗窗口
   只保留文字区（128→64 虚拟像素）。这样"整窗命中"就等于"文字区命中"：**下半部空白区
   不再属于窗口，也就不再挡点击**（原来下半部是窗口的一部分，alpha=1 时连点击一起挡）。

**效果**：
- 信息窗：整窗（=文字区）可拖动；下半部空白区完全穿透；显示无变化；
- 模拟时钟：整窗可拖动；倒计时：保持原样；
- 不会再出现"文字下方黑线"（没有 alpha 填充边界了）。

**曾尝试并已放弃的方案（勿再走）**：任何在幽灵绘制路径上挂钩的做法——改 allclear 的
填充边界、ULW 提交前清零像素、给窗口设置 SetWindowRgn 区域——实测都会让 SSP 启动即崩
（first.dll+0x3AF2 空指针/挂起）。原因：幽灵在该时机对"被包装函数的栈参数清理
（`ret 4`）"与"渲染器内部状态"极敏感（misaki 的行指针函数不是只读的，会重置画布状态）。
对应代码均已从 `patch_dll.py` 移除。

**部署**：`python patch_dll.py "<ghost master 目录>"` 会同时构建并复制 first.dll 与
misaki.dll（misaki 首次部署自动备份为 `misaki.dll.bak`；项目内原始件在 `input/`）。

## 7. Todo/Notify 状态栏改大小后文字重影（已修复：CreateParams 补 CS_HREDRAW）

- **现象**：拖动改变 Todo / Notify 窗口大小后，底部状态栏提示文字（"信息"）出现
  重影/发虚，重开窗口才恢复。**原版（未打补丁）同样存在**；实测外部强制
  `RedrawWindow` 一次即恢复，说明是"旧像素未擦除"。
- **根因**：VCL 给 `TStatusBar` 注册的窗口类样式 = `CS_VREDRAW | CS_DBLCLKS`（**缺
  `CS_HREDRAW`**，实测读数 0x9）→ 改变宽度时系统不做整窗失效 → 状态栏不整体重绘。
  跨进程 `SetClassLong` 改不了（写后读回仍是 0x9）。
- **修复**：在 `TWinControl.CreateWnd`（0x435294）调用虚拟方法 `CreateParams` 的指令处
  `0x4352C1`（`call [ecx+0x90]`；调用前 `mov ecx,[eax]`，`eax`=控件对象、`ebp`=CreateWnd
  栈帧）改为 `call` 到 `.cave+0x22C0` 的透明桩：
  1. 补完原 `call [ecx+0x90]`；
  2. 比较栈帧里正在填充的 `Params` 的类名缓冲（`[ebp-0x40]`/`[ebp-0x3C]`）是否为
     `"TSta"`/`"tusB"`（即 `TStatusBar`）；
  3. 命中才 `or dword [ebp-0x68], 2`（`WindowClass.style |= CS_HREDRAW`），随后 `ret`。

  其余窗口类完全透明（只多两条比较）。**不碰 `RegisterClassA` / 类注册 / 退出流程。**
- **效果**：Todo / Notify 拖动改大小后状态栏即时整体重绘，"信息"不再重影；其它窗口
  行为不变。
- **曾尝试并放弃的修法（勿再走）**：
  1. 挂钩 4 处 `RegisterClassA` 调用（0x414627 / 0x435396 / 0x4475AC / 0x44EB69 →
     跳板 0x406EDC），注册前给窗口类补 `CS_HREDRAW`（先对所有类、后改为仅 `TStatusBar`）
     ——两次都导致 SSP 启动后幽灵不显示、随后走进 SSP 自身的"卸载幽灵"路径并触发野
     WndProc 崩溃（与 9/24 记录的 SSP 偶发退出崩溃同款）。该环境对注册/退出等早期路径
     的挂钩极敏感，代码已从 `patch_dll.py` 移除。
  2. 挂 Todo/Notify 的 `FormResize`（0x463E78 / 0x464FC4，来自 DFM 方法表）在桩尾补
     `RedrawWindow(窗体 hwnd, 0, 0, 0x85)`——实测无效。
- **实现注意（踩过的坑）**：原指令是 6 字节 `FF 91 90 00 00 00`（`call [ecx+0x90]`），
  桩必须用 `call`（`E8 rel32` + 第 6 字节 `90` NOP）进入——**不能用 `jmp`**：`jmp` 不压
  返回地址，桩尾 `ret` 会弹栈上垃圾地址，导致所有控件创建流程错乱（表现为主菜单点任何
  选项都没反应）。

## 8. 退出/重载/人格切换修复（patch_exit_fix）

**现象**（都出自"卸载时序"这一条链）：

1. **退出崩溃**：WER 记录 `ssp.exe`、出错模块 `first.dll_unloaded`，故障偏移 `0x1476a`
   （也见过 `0x7474`）——卸载之后仍执行到已卸载模块的代码；随版本还可能表现为
   进程残留不退、时钟/文字残留、CPU 100% 自旋；
2. **重载 [SYSTEM]**：开发面板"显示错误日志"每次重载刷一条
   `SHIORI(unload) | Critical | [SYSTEM] Exception Raised at <值>`（故障地址 = DPI 上下文值一族）；
3. **尺寸类**：开着窗口退出后存档 ×1.5（150% 屏）；重载后 SSP 整体放大；
   切换到别的人格后，对方/SSP 新建的窗口整体放大。

**机制**：

- 退出流程：关精灵窗 → 经导出表调 unload（RVA `0xAA234`）→ 之后 SSP 才 `FreeLibrary`；
  卸载后残留的"僵尸活动"（窗口消息派发、收尾遗留调用）落到已卸载模块代码上 → 崩溃。
  断路必须落在"模块自身收尾/存档之后、卸载那一瞬之前"：过早破坏收尾（换 0x2E44 一族），
  过晚永远慢一步（`0x1476a` 就发生在卸载瞬间，轮询追不上）；
- 窗体尺寸/坐标的存档（保存函数 `0x462848`）按**调用线程的 DPI 上下文**输出：
  手动关窗走 request 包装（线程 `UNAWARE_GDISCALED(-5)`）→ 读到 96dpi 虚拟坐标（正确）；
  退出析构若跑在感知上下文 → 坐标被"提升"为物理像素（×1.5）。所以卸载全程
  （含 detach 期间**模块内部对 0xAA234 的直接调用**触发的"迟到存档"）线程必须保持 `-5`；
- 归还（恢复旧上下文）的时机还必须**不依赖"下一次加载谁"**：切人格时加载的是对方的
  SHIORI——任何挂在"本模块 load 路径"上的归还都不会运行 → 线程残留 `-5` →
  之后新建的窗口全部被 GDI 放大。

**定稿实现（全同步：无定时器/辅助线程/轮询；时序由调用序保证）**：

1. **unload 入口保持原始字节**；把 unload 导出经 EAT 重定向到存根 —— SSP 的调用进入
   存根，模块内部对 `0xAA234` 的直接调用仍走原函数（无需也不应接管）；
2. **存根**（`.cave+0x2400`）：线程切 `UNAWARE_GDISCALED`（旧上下文写暂存槽 `.cave+0x23F4`，
   并 `SetPropA` 挂到 SSPMAIN 的 `"dpictx"` 属性）→ 双销毁注册窗体（Tnotifyform 槽
   `0x4B08CC`/VMT `0x464280`、Tfirstconfigform 槽 `0x4B298C`/VMT `0x468DC8`，RTTI 校验后调
   `TObject.Free` 跳板 `0x402E40`、槽清零；析构触发原生存档）→ `call` 原函数**完好入口**
   `0xAA234` 并等其返回 → 跳收尾；
3. **收尾例程**（`.cave+0x226A`）：只做 EnumWindows 断路（WndProc 落在
   [模块基址, +0x100000) 的窗口换成 `DefWindowProcA`）；**不做 DPI 恢复**——线程保持 `-5`；
4. **归还（V7）**：在 DllMain 的 `DLL_PROCESS_DETACH` 末尾（入口 detour）——原 DllMain
   执行完（此前的清理/迟到存档全部结束）后，从 `"dpictx"` 属性读回旧上下文归还，再交还
   loader。触发点 = "本模块自己的卸载"，与下一个加载者无关：**重载 / 切人格 / 退出全覆盖**。

**布局（.cave 固定偏移）**：

| 偏移 | 内容 |
|---|---|
| 0x226A | 收尾例程（只断路，不恢复） |
| 0x2360 | 枚举回调 |
| 0x23F4 | 旧上下文暂存槽（存根写） |
| 0x2400 | 存根（切-5 + 存属性 + 双销毁 + call 完好入口 + 跳收尾） |
| 0x2600 | 窗口类名 `SSPMAIN-3145fdab-2ee0-4158-a1ce-832b553ad790` |
| 0x2630 | 属性名 `"dpictx"` |
| 0x2640 | V7 归还桩（DllMain detach detour） |
| 0x2700 | V7 入口跳板（原序言 6 字节 + 跳回入口+6） |

**实现要点**：

- DPI 切换复用 `.cave+0xB0` 的 `SetThreadDpiAwarenessContext` 指针槽（包装桩惰性解析；
  空槽 = 旧系统无该 API → 相关段整段跳过）；不要依赖弹窗/对话框行为做任何判断
  （本进程 MessageBoxA 被 SSP 改写）；
- 枚举回调取 hwnd 用 `[esp+0x24]`（pushad 后）；模块基址 = "回调自身地址 − 回调 RVA" 现算；
- V7 归还桩以"调用"方式执行原 DllMain（返回值经 pushad 槽还原给 loader），
  `reason == DLL_PROCESS_DETACH(0)` 才归还；归还序列只用 IAT/惰性解析的 API；
- 构建时脚本做：区域全零预检、入口/序言吻合校验、各段长度断言——不符直接报错拒出。

**验证（自动化）**：

- 重载 ×3：错误日志 0 条 [SYSTEM]；退出：WER=0、无崩溃弹窗、35 窗全关；
- 存档：模拟时钟 96×96 → **64×64**、文字信息窗 222 → **64×148**（= 逻辑值）；
- 重载前后开发面板矩形 (1414,81)-(1633,566) 逐像素一致；切人格来回无"整体放大"；
- 偶发"0x2E44 一族"（助手线程卸载期 Free 失效对象）为预存残余，与本层无关。

**部署与重建**：`python patch_dll.py "<ghost master 目录>"`（不带参数只写 `output/`）；
产物 = `output/first.dll`（与 misaki.dll 一并部署）。

## 9. 输入法（新版微软拼音）修复（V9：候选框感知修正根治）

**现象**（仅 96dpi 虚拟化的 GDISCALED 窗口：骰子 / 打字游戏 / Todo / Notify 等；SSP 自有窗口不受影响）：

1. 候选框位置 ×1.5 偏移（相对光标过远，首字母起即错）；
2. 组字窗文字过小（系统 150% 缩放下仍按 100% 字号渲染）；
3. 组字窗尺寸不随文字（字号修大后被截断）；
4. 组字窗相对光标偏移。

**根因分析：**

- **候选框（根治）**：GDISCALED 幽灵窗口下，MSCTF 在三个 `ClientToScreen` 站点
  （`msctf+0xE55D1`/`+0xE55DD` 光标矩形两角、`+0xEB083` 布局矩形）算出的**锚点已是物理值**。
  **新版**微软拼音的进程内管线（`textinputframework.dll`）在每键锚点计算后对输入控件调用
  `GetWindowDpiAwarenessContext`（实测 222 次/轮；两个站点返回地址
  `textinputframework+0x93642/+0x9365C`，查询对象为骰子窗口的 TEdit 输入框），按其判定
  "未感知应用"对锚点**再补一次 ×f 缩放** → 候选框二次放大（偏右下）。**旧版**微软拼音经
  `msctfuimanager.dll` 进程内 UI 直用原值，因此原本正确、且不经这段管线——这正是
  "源头单值无法兼容"的结构性原因。**修法（感知修正层）**：钩
  `user32!GetWindowDpiAwarenessContext`，命中上述两站点时回答 PMv2（物理感知）→ 补偿不再
  发生；源头锚点保持原值。对两版引擎一致，无需分流判别。其余换算点（0x4774F/0x30737）
  属于组字窗摆位自己的链，**不能动**（动了组字窗消失：摆位函数 0x476FD 的 PtInRect 门控
  会因上游坐标被改坏而 E_FAIL）。
- **组字窗文字**：画出的字 = 绘制每帧 `SelectObject(dc, [obj+0x18C] / [obj+0x194])` 选中的
  **缓存字体**；该缓存只由"字体设置事件"重建（正常打字/切窗口不重建）；每键的
  `ImmGetCompositionFontW` 读取只喂布局测量，不喂绘制。→ 字号放大必须落在
  **"SelectObject 替换字体"处**（每帧生效、无需反复触发）。
- **组字窗尺寸**的测量使用同一缓存字体对象，但调用点不在绘制四点 → 匹配需按
  "**对象==缓存源句柄**"（任意调用者），而非仅按调用点。
- **基线微偏**：组字窗摆位对齐用"应用上报的光标行"（旧字号语义），文字按放大字号渲染，
  相对基线略高（≈半个小写字母 o）。经与放大字号无关的验证后判定为可接受残差，不做补偿。

**最终实现**（集成于 `patch_dll.py` 的 IME 段，`IME_ENABLE` 总开关；全部位于 `.cave`，
位置无关代码，随 DLL 加载安装、卸载还原，无外部工具、无定时器）：

- **感知修正层（候选框根治件，独立子层）**：`user32!GetWindowDpiAwarenessContext` 入口钩
  （独立安装/还原/跳板，链入 load/unload；常量 `AWRFIX_*`）。桩流程：懒解析
  `textinputframework.dll` 基址（GMH 缓存）→ 返回地址 == 基址+`0x93642`/`+0x9365C`
  → 回答安装时取得的 **PMv2 规范句柄**（`SetThreadDpiAwarenessContext(-4)` →
  `GetThreadDpiAwarenessContext()` → 还原旧上下文）；其余调用原样转真函数。
  版本护栏：站点精确比对，失配自动降级直通（功能静默失效、无副作用）。
- **宿主判别（兼容原版 MATERIA）**：安装时调 `shcore!GetProcessDpiAwareness(当前进程)`；
  结果 == `DPI_AWARENESS_UNAWARE(0)`（原版 MATERIA 等 unaware 宿主，其 IME 由系统原生
  正确处理，无需任何修正）→ **整个 IME 层 no-op**（不装任何钩，含感知修正层）。
  仅 aware 宿主（SSP = PER_MONITOR_AWARE）装钩生效。实测值：SSP 进程感知=2、
  MATERIA=0；两边的打字输入框都是 GDISCALED/dpi=96（窗口级相同、无法区分），
  故必须以**进程级**感知为判别信号。
- **钩1（ClientToScreen 门控）**：user32!ClientToScreen 入口钩；返回地址 ∈
  `{msctf+0xE55D1, +0xE55DD, +0xEB083}` 且焦点窗口 `GetDpiForWindow()==96` 时：
  EB083 顺带记录**原始输出为原点 O**（槽 OX/OY，供钩3）+ 刷新动态因子；输出值
  **保持原样**（原先的 ÷f 已被感知修正层取代、整体移除）。
- **钩2（SelectObject 换字体）**：gdi32!SelectObject 入口钩；返回地址 ∈ 绘制/度量四点
  `{0xE40ED, 0xE413C, 0xE3EEA, 0xE3F0F}` 或对象 == 已缓存源字体句柄（任意调用者）→
  替换为自建 **×f 字体**（`GetObjectW→lfHeight/lfWidth×f→CreateFontIndirectW`，
  两句柄缓存、惰性创建）；同一 DPI 门控。
  **桩顶先做因子刷新 + 缓存对账**：若当前因子 ≠ 缓存建立时因子（CACHEF），清空四个
  句柄缓存再走判定——否则倍率切换后 msctf 仍选**同一个原字体句柄**，会在
  `obj==SRC` 处命中旧缓存直接复用旧字号（这正是"位置跟随了但字体不跟随"的原因）。
- **钩3（摆位偏移补偿）**：`msctf+0x47A8A`（SetWindowPos 调用点，原 6 字节
  `FF 15 8C 51 EE 76` = `call [msctf+0x10518C]`，地址字节随 ASLR、由运行时从调用点原样
  搬运）改桩；`x' = O + f·(x−O)`（即相对原点缩放；O=0 时跳过；f=1 恒等）。
- **动态因子（实时跟随系统缩放）**：GDISCALED 线程上下文里多数 DPI 查询会被虚拟化或
  进程级缓存而失真——实测 `GetDpiForSystem` 与 `GetDeviceCaps(GetDC(0),88)` 在幽灵线程里
  均恒返 96（或进程启动时值），不会跟随运行中切档。最终方案：取因子时把线程**临时尖峰到
  PMv2**（`SetThreadDpiAwarenessContext(-4)`）→ `GetDpiForMonitor(MonitorFromPoint((0,0),
  MONITOR_DEFAULTTONEAREST), MDT_EFFECTIVE_DPI)` 取真实系统 DPI → 恢复原上下文；
  `f = 系统DPI/96`（每次现算）。实测切档（192/168/120 等中间值）全部准确，无定时器、无轮询。
  **96dpi/MATERIA 时全恒等 no-op**。
- **装配与还原**：`load` 导出经 EAT 重定向到"载入包装"（`call 安装例程` 后转原包装）；
  `unload` 同理先还原再转；安装例程经 `GetModuleHandleA/GetProcAddress`
  （first.dll IAT 槽 `0x4B31E4/0x4B31E0`）解析目标函数，`VirtualProtect` 后写 E9 热补丁，
  并保存原序言供还原（还原时以首字节==E9 判定）。`GetDpiForMonitor` 属 shcore.dll：
  先 `GetModuleHandleA`，未加载则 `LoadLibraryA` 兜底。因子链槽位：
  `0xFC`=SetThreadDpiAwarenessContext、`0x08`=MonitorFromPoint、`0x3C`=GetDpiForMonitor、
  `0x40`=LoadLibraryA（槽 `0x1C` 空闲，旧 GetDeviceCaps 占位已在收尾清理中移除）。
- **栈平衡教训（排障存档）**：钩子内联调用 API 必须按被调方约定核算 push/pop——stdcall
  由被调方清理参数，**调用方不可再 pop 参数**。曾因在 `GetDpiForMonitor` 的 call 之后
  又补 pop 一次（把已被 ret 16 清掉的句柄参数当作仍在栈上），安装例程净差 +4 字节，
  收尾 `popal` 从错误位置恢复整帧 → 返回地址变野值、加载即崩（现象为
  `[SYSTEM] Exception Raised at 00000000 ... (Writing 00000000)`）。新增内联调用后，
  请把成功/失败各分支的栈深度画一遍再验证。
- **曾试验但未采用**：ImmGetCompositionFontW 入口缩放钩（窗口自适应由钩2的缓存匹配覆盖，
  A/B 验证不需要，已移除）；ImmSetCompositionFont 反复重设方案（需触发、有延迟，已废弃）。

**关键地址表**（msctf.dll，RVA）：

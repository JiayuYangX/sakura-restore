# first.dll 能量机制分析及修复（さくら人格）

> 分析对象：`input/first.dll`（2002 年 MATERIA 内置人格 さくら 的 SHIORI 核心，Delphi 编译）
> 分析方法：objdump 静态反汇编 + SSP SHIORI 日志 + 运行时内存采样（管理员 PowerShell）
> 分析日期：2026-09-01 ｜ 环境：SSP 2.8.85 / Windows 11 25H2

---

## 1. 结论速览（TL;DR）

**机制：**

| 主题 | 结论 |
|---|---|
| 睡眠循环 | 清醒秒数 ≥ 能量阈值（0xab31c 按能量分级）→ 说「ねむねむ」→ 30 秒后小睡（mode 2）→ **只能双击戳醒**（无自然醒，属设计） |
| 能量 | 清醒 -1/分钟、小睡 +3/分钟（上限 360）、泡澡醒来 +50；调试项直接写值（最困=0 / 最不困=360） |
| mode 3 | **= 泡澡状态，不存在"夜间睡眠"**；两个入口（调试「風呂へ」/ 夜间自然触发）共享同一状态与文本 |
| 夜间泡澡 | 21-5 点 + 放置 22.5 分钟 + `bathflag==0`；泡过一次澡后 `bathflag=1` 锁 **720 分钟（12 小时）**，只有冷却检查能清零 |
| 时间无关性 | 小时调用点全量审计：睡眠/能量逻辑**无任何绝对时间依赖**（唯一例外 = 泡澡入口的 21-5 点检查） |

**故障与修复：**

| 补丁 | 位置 | 问题 | 修复 | 效果 |
|---|---|---|---|---|
| 1 | `0x719E9` | NOTIFY 请求一律返回 400 → 秒级状态机冻结 | 6 字节 `jne` → NOP | NOTIFY 进事件分派（400→204），状态机全程运转 |
| 2 | `0x79E08` | `\![enter,inductionmode]` 诱导模式 cantalk 恒 false → 对话全被丢弃、永久卡死 | 字符串长度字段 23 → 0 | 泡澡/入睡不再进诱导模式，R3 恢复 1，对话正常 |

## 2. 睡眠与能量循环（机制核心）

### 2.1 状态机

```
mode 0（清醒）─── 清醒计数器(0x4adc9c) ≥ 困倦阈值 ──→ mode 1（困倦，说「ねむねむ……」）
mode 1 ── +30 秒 ──→ mode 2（小睡，说「くー……」+ \![enter,inductionmode]）
mode 2 ── 双击戳醒（2~4 次）──→ mode 0
mode 3（泡澡）── 倒计时自动醒 ──→ mode 0（详见 §3）
```

### 2.2 困倦阈值 = 能量分级（0xab31c，非随机）

| 能量 | 等级 | 困倦阈值（清醒秒数） |
|---|---|---|
| 0 ~ 30 | 3 | **30 秒**（几乎立刻困） |
| 31 ~ 120 | 2 | 900 秒（15 分钟） |
| 121 ~ 240 | 1 | 1800 秒（30 分钟） |
| 241 ~ 360 | 0 | 3600 秒（60 分钟） |

能量越低困得越快——"低能量反复入睡、高能量保持清醒"的自调节闭环。

### 2.3 能量变化规则（OnMinuteChange 处理器 0x71F19）

| 场景 | 变化 | 代码位置 |
|---|---|---|
| mode 2（小睡中） | **+3/分钟**（上限 360） | 0x71F35 |
| mode 0/1（清醒，非最小化） | **-1/分钟**（下限 0） | 0x71F88 |
| mode 0/1（最小化，0x4adc94=1） | 不衰减 | 0x71F86 跳过 |
| mode 3 醒来 | **+50**（上限 360） | 0x71E7D |
| 调试「最困状態」 | **= 0** | 0x77D77 |
| 调试「最不困状態」 | **= 360** | 0x77D9D |

### 2.4 清醒计数器（0x4adc9c）

- 递增：**0x69D58** `inc [eax]`——经 DATA 指针表 `0x4AE090`（fileoff 0xACC90）间接加载地址后递增
- 门控：mode ∈ {0,1} 时 **+1/秒**（内存采样验证）；mode == 2 时冻结，改增另一计数器 0x4adc98
- `0x4adf4c` 是指向 mode（0x4b29e8）的**指针**，非独立状态
- 因 `inc [eax]` 无直接地址引用且地址藏在 DATA 指针表，纯静态字节搜索无法发现

### 2.5 mode 2 唤醒（OnMouseDoubleClick 处理器 0x776A0）

双击行为按状态分派：

| 状态 | 双击结果 |
|---|---|
| 清醒（0x4b2a70="1"） | 显示上下文菜单 |
| mode 1（困倦） | **立即醒**：「寝てないですよっ！」mode=0 |
| mode 2（小睡） | 唤醒计数器 -1；≠0 → 睡眠话（んー/むー/うーん/あ…/ん…/んん… 随机）；**=0 → 唤醒**（「ん……あ。」/「な、何かな？よだれ拭きや」），mode=0 |
| mode 3（泡澡） | うにゅう吐槽：「ただのかんばんのようだ。」，**不唤醒** |

唤醒计数器（0x4adca4）机制：

```
入睡时：随机(2)+2 = 2~3      （0x71CAA / 0x71DB2）
小睡中：每分钟 +1，封顶 4     （0x71F52，与 +3 能量同分支）
双击时：-1                   （0x776EE）
归零   → 唤醒
```

**结论：mode 2 无自然唤醒——设计如此，不是 bug。** 唤醒通道只有"双击戳醒"（需 2~4 次，睡得越久戳得越多）。菜单「部屋で寝かせてあげたら？→minimize」佐证设计意图（最小化 = 让她在屋里睡）。

## 3. 泡澡机制（mode 3）

### 3.1 状态定义

**mode 3 只有一种含义：泡澡（入浴）状态，不存在"夜间睡眠"。** 夜间触发的含义是"她决定去泡个澡"（放松/就寝仪式）。

两个入口，共享同一状态、同一倒计时、同一醒来逻辑、响应文本完全相同：

| 入口 | 代码位置 |
|---|---|
| 调试菜单「風呂へ」（On_debug_furo） | 0x77D2B |
| 夜间自然触发 | 0x71DF3 |

```
mode = 3
0x4adc88 = 随机(10..19)×60 = 600~1140 秒（倒计时）
响应 = \![enter,inductionmode] + 泡澡主文本（0x79F94）
```

夜间入口的响应文本（= 泡澡主文本）：
> 「あ‥‥もうこんな時間か‥‥じゃ、ちょっとお風呂入ってくるよ。」（啊…已经这个时间了…那么，我去泡个澡。）

### 3.2 夜间入口条件与流程

```
bathflag == 0（12 小时冷却，见 3.3）
+ 时间 21:00~5:00（小时 ≥21 或 ≤5）
+ 清醒计数器 ≥ 1350（放置 22.5 分钟）
+ mode 不在 {2,3}
→ mode 3 泡澡，倒计时 600~1140 秒
```

到期自动醒（倒计时 0x4adc88 每秒递减，0x71E32）：

```
\![leave,inductionmode] + 「ただいま。・・・！」+ energy +50 + mode=0 + 计数清零 + bathflag=1
```

- 时长实测：15 分钟 = 900 秒 ✓
- **双击不能提前结束**（只回"立牌"吐槽）

### 3.3 bathflag 冷却：720 分钟（= 12 小时），不是 720 天

**bathflag = "近期泡过澡"标记**，仅 3 处写入：

| 位置 | 值 | 场景 |
|---|---|---|
| 0x71EA8 | =1 | 泡澡正常结束（mode 3 到期） |
| 0x78B4D | =1 | 泡澡中（mode 3）关闭人格（うにゅう：「風呂行っとる間に終了か…ええんか？」） |
| 0x71ED1 | =0 | 冷却检查：`|现在 − lastbathdate| ≥ 720`，每秒执行；清零同时把 lastbathdate 更新为当前时刻（0x71ED8，唯一写入点） |

**720 的单位是分钟**（反汇编证据）：日期差函数 0x1c4a4 调用 0x1c460 计算 `year×365×24×60 + 月累计天×24×60 + day×24×60 + hour×60 + min`，全程按分钟累加（0x1c3bc 为月→累计天数跳转表），比较对象 `0x2d0` = 720 分钟 = **12 小时**。

**实际影响**：夜间入口要求 `bathflag==0`（0x71DBF）——泡过一次澡后夜间泡澡被锁 12 小时；调试「風呂へ」直接写 mode=3，绕过此锁（测试泡澡的唯一便捷入口）。

### 3.4 时间无关性验证（小时调用点全量审计）

**能量系统与睡眠行为与当天绝对时间无关。** 小时获取（0x17a4c）全部 12 处调用点：

- 夜间泡澡入口检查（0x71DC1/0x71DCB）← **唯一与睡眠相关的绝对时间依赖**
- 日期函数内部（0x1C5B9）、时间格式化显示（0x6639B、0x6753D、0x6758B）、随机对话（0x781B8）、日间问候日程（0xA5528~0xA5BDA）

mode 转移、能量增减、困倦阈值、唤醒逻辑均无时间条件；bathflag 冷却（720 分钟）也是相对时间（距上次清零），非绝对时刻。

## 4. 数据存储

### 4.1 运行时（内存）

| 全局变量 | 含义 |
|---|---|
| `0x4adca0` | **能量值**（DWORD，范围 0~360） |
| `0x4adc84` | bathflag（泡澡标志） |
| `0x4adc88` | mode 3 泡澡倒计时（秒） |
| `0x4adc94` | 能量衰减抑制标志（最小化=1 暂停衰减） |
| `0x4adc98` | 睡眠相关计数器（多处清零） |
| `0x4adc9c` | **清醒计数器**（放置时长，阈值比较用） |
| `0x4adca4` | **唤醒计数器**（入睡 2~3，睡眠中 +1 封顶 4，双击 -1） |
| `0x4b29e8` | **mode 状态**：0=清醒 / 1=困倦 / 2=小睡 / 3=泡澡 |
| `0x4b2a70` | 字符串状态指示（"0"=睡眠处理，"1"=正常上下文菜单） |

### 4.2 持久化（存档 `ghost/master/var/first.txt`）

```
energy,173              ← 能量值（对应内存 0x4adca0）
energychecksum,<md5>    ← 校验和（防作弊：直接改存档 energy 会被识破）
```

- 加载例程（0xA76xx）：解析 `energy` 存入 `0x4adca0`（0xA76F6）并校验

## 5. 兼容性故障与修复（补丁 1 & 2）

### 5.1 背景：同一兼容性错位的两个环节

2002 年的 first.dll 与 2026 年的 SSP 之间，SHIORI 协议的**实现**与**规范**发生错位：

- **旧时代**（MATERIA）：所有事件一律以 **GET** 发送（旧规范明言"cantalk=0 时仍以 GET 送达"，作者备注承认实现偷懒）
- **新时代**（SSP 2.5.33+）：严格按规范——cantalk=0（不能播对话）时背景事件改用 **NOTIFY**

first.dll 按旧时代行为编写，只实现了 GET 路径。两个补丁分别修补断裂的两端：

- **补丁 1 = 接收端**（"聋"）：让 NOTIFY 也能进事件分派
- **补丁 2 = 触发端**（"哑"）：消除诱导模式这一**永久** cantalk=0 的来源

### 5.2 补丁 1：NOTIFY 请求被 400 拒绝（0x719E9）

**现象**：人格困倦程度不随时间变化、泡澡永不结束；SSP 日志 `NOTIFY SHIORI/3.0` + `ID: OnSecondChange` → `400 Bad Request`。系统时间读取正常（墙钟独立工作），造成"其它都正常"的假象。

**根因**（反汇编证据）：请求解析器（Delphi 编译）：

```
0x7136F  mov edx, 0x47A648        ; 响应默认初始化为 "SHIORI/3.0 400 Bad Request"
0x7175B / 0x7195A                  ; "GET" 前缀 → 正常事件分派
0x717E4                            ; "NOTIFY" 前缀 → 只处理 5 个信息查询 ID
                                   ;   (uniqueid/hwnd/ownerghostname/otherghostname/installedghostname)
0x719E9  jne 0x7989e               ; ★ 其它 NOTIFY（如 OnSecondChange）→ 带 400 直接退出
```

first.dll 认识 "NOTIFY" 这个词，但**只实现 5 个查询类 ID**；普通事件的 NOTIFY 一律 400 → 秒级状态机（困倦累积、泡澡计时、AI 对话调度）全部冻结。

**修复**：NOP 掉 0x719E9 的 6 字节条件跳转（`0F 85 AF 7E 00 00` → `90 90 90 90 90 90`），任何方法都落入事件分派。NOTIFY 返回的脚本按协议被 SSP 忽略，不影响显示行为；GET 路径完全不受影响。

**验证**：`NOTIFY OnSecondChange` 从 400 变为 **204**；泡澡 15 分钟正常到期、energy 动态变化、AI 对话每 ~2 分钟生成；NOTIFY 特殊 ID 也恢复正常应答。

### 5.3 补丁 2：诱导模式永久卡死（0x79E08）

**现象**（补丁 1 之后）：泡澡结束语「ただいま。・・・！」看不到、泡澡立牌不恢复、所有背景对话"哑巴"；日志 R3=0 连续数小时，OnSecondChange 一直 NOTIFY。

**根因**（因果链）：

```
泡澡开始 → enter,inductionmode（GET 响应，执行成功）→ 诱导模式
  → 诱导模式 cantalk 恒 false（"ゴースト終了まで有効"，只解除超时/最小化/结束 3 条限制）
  → R3=0 → 背景事件改走 NOTIFY（SSP 规则）
  → 泡澡 15 分钟到期 → 人格在 NOTIFY 响应里返回 [leave,inductionmode + 结束语]（唯一退出时机）
  → SSP 按 NOTIFY 规则丢弃返回脚本 → leave 从未执行
  → 诱导模式永久有效 → R3 恒 0 → 死循环
```

`\![enter,inductionmode]` 是独立字符串（marker 0x79E04 / 长度 0x79E08=23 / 数据 0x79E0C），被**泡澡、mode 1→2 入睡**两处拼接使用（0x71D52、0x71E12）。

**修复**：把 0x79E08 长度字段 23 → 0（`17 00 00 00` → `00 00 00 00`，实际只改 1 字节）。三处拼接得到空字符串 → 泡澡/入睡不再进入诱导模式；R3 恢复 1 → 背景事件回到 GET；残留的 `leave,inductionmode` 对未进入的模式是无害空操作。

**验证**：OnSecondChange 从 NOTIFY 恢复为 **GET**（16:44 起连续 GET）；泡澡结束语正常显示（OnBalloonTimeout 铁证）；立牌自动恢复；AI 对话每 ~2 分钟正常显示；睡眠流程同样修复。

### 5.4 补丁关系与部署状态

| | 补丁 1（0x719E9） | 补丁 2（0x79E08） |
|---|---|---|
| 修复对象 | first.dll 接收端（"聋"） | 触发端（"哑"） |
| 作用 | 任何原因 R3=0 期间事件仍被处理 | 消除诱导模式这一永久 R3=0 来源 |
| 必要性 | R3=0 在正常使用中频繁出现（气球显示、被动模式等），无补丁 1 则状态机在这些时段冻结 | 光有补丁 1，泡澡/睡眠期间 R3 永久 0，说的话全被丢弃 |

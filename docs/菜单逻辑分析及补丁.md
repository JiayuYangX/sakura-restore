# first.dll 菜单逻辑分析与补丁（双击 / 搜索框 / 小游戏窗体）

> 本文档记录"菜单相关"的全部分析与补丁：角色双击行为、搜索/输入框标志维护、
> 打字/问答/视力三个小游戏的窗体与退出处理。
> 链接相关（人名加链接、RSS 头条打开浏览器）见《链接机制说明及补丁.md》。
> 地址约定：**文件偏移 = VA − 0x400C00**（CODE 段；反向 VA = 文件偏移 + 0x400C00）。
> 所有补丁集成在 `patch_dll.py`，可从 input/first.dll 一键重建。

---

## 1. 现象与背景

### 1.1 双击回主菜单

- SSP 双击角色会发送 `OnMouseDoubleClick`；first.dll 的处理分支
  （入口 VA 0x4782BD / 文件 0x776BD）会重新输出主菜单脚本 → 于是"双击回主菜单"。
- MATERIA（原版基座）的旧事件模型在"选择肢/菜单等待中"**不派发**角色鼠标事件，
  所以原版只能点「取消」返回。
- SSP 设置项 `Balloon.LeftDoubleClick.Method`（不执行任何操作等）**不控制该事件**，实测无效。

### 1.2 SSP 请求里的 Status（实测分布）

| Status | 含义 |
|---|---|
| `talking,...` | 对话进行中（文字还在显示/播出） |
| `choosing,...` | **选择肢/菜单等待中** |
| `passive,...` | **小游戏进行中** |
| `balloon(...)` / 无 | 空闲 |

### 1.3 小游戏窗体（都是 DLL 自己创建的 Delphi 窗体，不是 SSP 的框）

| 类名 | 用途 | 关闭行为 |
|---|---|---|
| `Ttypinggameform`（含子窗 `TEdit`） | 打字游戏的输入框 | `FormCloseQuery`(需 [Self+0x321] 已提交) → `FormClose`=caFree（销毁） |
| `Teyesightform` | 问答第一题的 C 图窗；视力检查共用 | `FormCloseQuery` 无拦截（0x4704EC 直接 ret）；`FormClose`=caFree（0x470544） |
| `Tcountdownform` | 倒计时显示窗（FormCreate 0x46F104 / FormPaint 0x46F284 / timerTimer 0x46F488） | 无 `FormClose` → 关闭=**隐藏(caHide)**，可复用 |

## 2. 双击判定（桩B：`.cave+0x500`，挂 0x4782BD）

按优先级：

1. 请求含 `"Status: choosing"`（选择肢/菜单等待中）→ **吞掉**（清响应跳 0x478848，SSP 收 204）。
   配合 SSP 设置「左双击 = 不执行任何操作」即完全无反应。
2. `SEARCH`=1（**搜索输入框开着**）→ 吞掉。
3. 请求含 `passive`（被动模式：问答/打字/教程等）：
   - `EYEBUSY`=1（**视力保护窗口：OnEy\* 置位→非被动双击解除**）→ 吞掉
     （整局含反馈期，防双击打断响应末尾的 `leave,passivemode`）；
   - 否则 → 菜单缓存（cave+0x960）非空则 LStrAsg 写回缓存菜单（显示出该层
     菜单，便于点「退出」）；为空则吞掉（空缓存头 rc=0，不能对它做 LStrAsg——
     引用计数/Freemem 风险，见 3.2 坑一）。
4. 非 passive → `EYEBUSY=0`（解除保护窗口）→ 清响应后跳 0x4782C5，走 ghost
   原逻辑（弹主菜单）。

注意：**不要**动 DLL 内部"点击/菜单状态机"字节 0x4B29E8——它在菜单流程里有自己的
状态转移，清零会破坏"菜单→开始"流程（曾导致点 Period 进不去）；它同时是发送函数
0x4ABC34 的开关（非 0 时静默跳过发送，见 3.2）。历史上一度在双击拦截出口/盒子弹出时
清过零，均被证实干扰菜单流程，**已全部移除**，不要再动这个字节。

实现要点：

- 请求扫描约定：**[ebp+8]=请求字符串指针（PChar）、[ebp+0xC]=指向长度的指针（DWORD\*）**
  （经 0x45F220 与 `System.Move`(0x40283C：EAX=源/EDX=目的/ECX=字节数) 联合反汇编确认）。
- 命中"吞掉" → 清响应（[ebp-0x1c]）后跳公共出口 0x478848（SSP 收 204）。
- 标志/缓存都在游戏状态区（由桩A 维护）：见第 3、5 节。

## 3. 状态维护与响应监控（桩A：`.cave+0x600`，挂 0x47A399）

挂在事件响应汇总点（所有响应都经过；request() 帧内，EBP 有效）。
读**事件名**（[ebp-0x4c]），按前缀分流：

| 事件名前缀 | 动作 |
|---|---|
| `OnUs`\*（输入框取消） | 仅 `Ref1=close`：取 `Reference0`（框 ID）→ `\![raise,<Ref0>,]`（空提交，见 4.3）；Ref0==`OnGoogle` → SEARCH=0；`Ref1=timeout` **不响应**（宿主原生兜底补发 ID 事件、Ref0=`timeout`，DLL 走「時間切れ」分支）；**不碰 EYEBUSY** |
| `OnGo`\*（OnGoogle 搜索提交） | SEARCH=0 |
| `OnQu`\* | `OnQuizLeave` → 置 PENDING+GAMELEFT+关窗体；`OnQuizEnter` → 清 GAMELEFT；其余（进度事件）→ 放行（不打断） |
| `OnTy`\* | `OnTypinggameLeave` → 同上；`OnTypinggameEnter` → 清 GAMELEFT；其余 → 放行（不打断） |
| `OnEy`\*（视力） | `EYEBUSY`=1（保护窗口开始；反馈期保持，解除只在桩B 非 passive 双击） |

事件名判定用前缀简称（`OnUs`/`OnGo`/`OnQu`/`OnTy`/`OnEy`；DLL 事件为闭集，
各前缀与子事件后缀组合唯一，无歧义）；仅响应扫描用全称
`\![open,inputbox,OnGoogle`（否则会误匹配视力/问答的框）。

其余固定动作（每次响应都跑）：

- **PENDING**（cave+0x948，问答/打字退出事件时置 1）：把 `CLOSE_CMD` 前置到
  本次响应最前面（仅一次）：
  `\![quicksection,false]\![close,communicatebox]\![close,teachbox]\![close,inputbox,__SYSTEM_ALL_INPUT__]\![leave,passivemode]`
  （关闭 SSP 侧输入框并退被动；问答/打字退出时 DLL 自身响应本来就以 `leave,passivemode`
  开头，属等价冗余；打字框是 DLL 自己的窗体，不靠这些命令，多关无副作用）
- **GAMELEFT**（cave+0x94C）：Leave 事件置 1、Enter 事件清 0；唯一用途是给打字窗
  `FormCloseQuery` 放行（见 4.4），让辅助桩发的 WM_CLOSE 能关掉未提交的自绘框。
  （历史上的 SWALLOW"退出后吞游戏残留事件"经实测无必要，已删除，0x94D 空闲。）
- **菜单缓存扫描**：响应里含 `\![*]\q[`（菜单脚本）→ 整条复制到缓存
  （cave+0x960，上限 0x6FC），供双击重放。
- **输入框标志扫描**：响应里含 `\![open,inputbox,OnGoogle`（全称）→ SEARCH=1。
- 最后复刻被覆盖的 `cmp/jne` 指令并跳回原路径（0x47A3B1 / 0x47A39F）。

### 3.2 踩坑记录：缓存头压到标志位 & 测试环境里的老 materia

**坑一：缓存头（refcount）压到 GAMELEFT。** 菜单缓存（cave+0x960）的
Delphi 字符串头是 `[refcount][len][data]`，refcount 写在缓存偏移 −4 处。
把数据区往右搬时必须给它留出这 4 字节空隙，否则每次写缓存都会把相邻的
标志字节（GAMELEFT 等）覆盖成 `0xFFFFFFFF` → 标志被误判（当年 GAMELEFT 还兼作
"退出后吞事件"开关，于是**所有游戏进度事件响应被吞**）→ 表现像"打字游戏点 Period
进不去/答完不跳下一题"。教训：**搬数据区后必须做区间重叠检查**（布局表见第 5 节，
已校验无重叠）。

**坑二：测试时同时开着老的 materia.exe。** 老 MATERIA 也监听/占用 SSTP，
会截走 DLL 通过 SSTP 发出的 `\![raise,OnTypinggameInput,...]`（表现为 SSP 里
冒出一个显示该脚本文字的气泡、游戏不推进）。**测试前务必确认没有其它
MATERIA/SSTP 程序在运行**（关掉 materia.exe 后重启 SSP 即恢复正常）。

> 附注：DLL 的发送函数 `0x4ABC34` 开头有 `cmp byte [0x4B29E8],0; jne ret`
> （该字节是原版双击/菜单状态机的状态，非 0 时静默跳过发送）。我们曾在
> 双击拦截出口 / 盒子弹出时清零它，均被证实会干扰菜单流程，**已全部移除**，
> 不要再去动这个字节。

### 3.1 坑：事件名 [ebp-0x4c] 必须装 SEH

对没有 ID 的请求（SSP 启动时的协议探测 `GET Version SHIORI/2.6` 等），
[ebp-0x4c] 是**未初始化的栈残留**，可能是小整数 → 直接解引用即崩；
Delphi 捕获异常后探测响应变 NULL/500，SSP 便降级为 SHIORI/2.2（该 ghost 只认 3.0），
所有事件都回 500、ghost 无法启动。

现在这段读取装了 SEH 保护：一旦异常，处理器把 Eip 改到收尾处，安全跳过事件名判定。

## 4. 小游戏退出流程（打字/问答一起处理）

### 4.1 流程

点击「退出」→ SSP 发 `OnQuizLeave` / `OnTypinggameLeave` → 桩A：

1. PENDING=1、GAMELEFT=1；
2. 调**辅助桩**（`.cave+0x400`）：按类名 `FindWindowA` 依次找
   `Ttypinggameform`、`Teyesightform`、`Tcountdownform`，找到就各发一条
   `WM_CLOSE`（异步 PostMessage，不会死锁）；
3. 本次（退出）响应前置 CLOSE_CMD → SSP 关闭输入框并正常播放 goodbye
   （`\![leave,passivemode]` 完整执行）。

### 4.2 为什么用 WM_CLOSE 而不是模拟回车

最初尝试模拟回车（WM_KEYDOWN/CHAR）关打字框，发现两个问题：

1. **raise 打断 goodbye**：打字框的 `editKeyDown`（0x46EAEC）在回车时会向 SSP 发
   `\![raise,OnTypinggameInput]`；SSP 处理 raise 事件会取消正在执行的
   `\![leave,passivemode]` → passive 不退、双击又进游戏。
2. **提示音**：单行编辑框对未消费的回车会 MessageBeep（"叮"）；
   DLL 自己的超时关闭走 Close 路径，所以它是安静的。

改成 WM_CLOSE 后走 DLL 的 Close 路径（与超时相同），既没有 raise 也没有键盘消息，
两个问题一起消失。

### 4.3 输入框取消：只剩"用户关闭"由我们补空提交（`.cave+0x4300` 辅助函数）

`OnUserInputCancel`（Ref0=框 ID，Ref1=close/timeout）由桩A 的 OnUs* 分支接管，
**只对 `Ref1=close` 生效**：在请求里找 `Reference0: `，把值抄进预置了
`\![raise,` 的 dstr、补 `,]`、更新 rc/长度，响应 `\![raise,<Ref0>,]`（空提交）。

**`Ref1=timeout` 一律不响应（204），交给宿主原生兜底**：

- 宿主对未应答的超时取消会**补发 ID 事件且 `Reference0="timeout"`**
  （干净日志实测：`OnUserInputCancel(OnQuizInput,timeout)→204` 紧接
  `OnQuizInput ref0='timeout'`）；DLL 的答题处理器对 `"timeout"` 有专属分支
  （0x47BF94 比较处）→ 输出「時間切れー。」；视力对 timeout 会进"错误"分支
  （与空提交一样，看不出差别）。
- 关闭（close）没有兜底，所以那段空提交必须由我们补。

Ref0==`OnGoogle`（搜索框关闭）时补空提交并清 SEARCH（搜索框无超时）。
取值失败/空值 → 不响应（204）。
**反馈期保护**：EYEBUSY 不在这里清——从 OnEy* 到「非被动双击」为止，反馈
台词期间的双击都被桩B 吞掉，保证 `leave,passivemode` 完整执行（否则脚本被
双击打断 → 卡在被动模式）。

### 4.4 CloseQuery 放行桩（`.cave+0x10D0`，挂 0x46EE00）

背景：打字框在**回车提交时会自毁**（`editKeyDown` 0x46EAEC：置 `[Self+0x321]=1`
后 `call 0x44C9DC` 释放窗体），超时同理——所以常规游玩它随提交消失；只有
**"词还没提交就退出"**时它才会留屏，需要辅助桩的 WM_CLOSE 来关。

`Ttypinggameform.FormCloseQuery` 原本是 `CanClose := [Self+0x321]`
（只有回车提交/超时才置位），辅助桩发 WM_CLOSE 时该标志为 0 → 会被拒绝关闭。
放行桩在 **GAMELEFT=1** 时直接 `CanClose=1`，其余情况保持原逻辑。
（`Teyesightform` / `Tcountdownform` 无此限制，不需要桩。）

### 4.5 结果

- 打字游戏退出：输入框立即关、无"叮"、goodbye 完整、passive 正常退；
- 问答退出：SSP 输入框 + C 图窗（`Teyesightform`）一起关；
- 倒计时窗（`Tcountdownform`）关闭（隐藏），与"回复后消失"行为一致。

## 7. 实测教训（踩过的坑）

- **同步调用会死锁**：不要在响应处理里同步调 DLL 的提交处理函数；必须 PostMessage 异步。
- **重定位**：模块实际基址不是 0x400000（见第 5 节）；绝对地址读写会读到别的内存
  （曾导致"所有回车都被当成退出拦掉"）。
- **不要写 [ecx]**：`editKeyDown` 在字符串构造调用之后 ecx 已被破坏，
  写它触发异常且 Delphi 异常派发器二次崩溃（STACKTRC 0x403AF2 的 rep movsd 空指针）。
- **[ebp-0x4c] 未初始化**：见 3.1。
- 改动 DLL 数据布局后，所有相对偏移（如桩B 读缓存的 [eax+0x20]/[eax+0x24]）要同步更新。
- **别让桩超出自己的槽位**：桩B 超过 0x100 会覆盖到 0x600 的桩A 首字节
  （曾把 `push eax` 盖成 `FF`，表现为"进入游戏直接回车崩溃"的前科）。
  构建时都有长度断言。
- **辅助桩（0x400）的接口约定**：以 ebx=cave+0x60B 为基址且不恢复 ebx。
  调用方需自设/恢复 ebx——桩A 天然满足；0x4300 取消辅助函数不碰 ebx（call/pop 自算基址）。
  辅助桩实际占 0x400-0x486，新代码别放进这一段。

# first.dll 菜单逻辑分析与补丁（双击 / 搜索框 / 小游戏窗体）

> 本文档记录"菜单相关"的全部分析与补丁：角色双击行为、搜索/输入框标志维护、
> 打字/问答/视力三个小游戏的窗体与退出处理。
> 链接相关（人名加链接、RSS 头条打开浏览器）见《链接机制说明及补丁.md》。
> 地址约定：**文件偏移 = VA − 0x400C00**（CODE 段；反向 VA = 文件偏移 + 0x400C00）。
> 所有补丁集成在 `patch_dll.py`，可从 input/first.dll 一键重建。

---

## 1. 现象与背景

### 1.1 双击回主菜单

- SSP 双击角色会发送 `OnMouseDoubleClick`；first.dll 的处理分支
  （入口 VA 0x4782BD / 文件 0x776BD）会重新输出主菜单脚本 → 于是"双击回主菜单"。
- MATERIA（原版基座）的旧事件模型在"选择肢/菜单等待中"**不派发**角色鼠标事件，
  所以原版只能点「取消」返回。
- SSP 设置项 `Balloon.LeftDoubleClick.Method`（不执行任何操作等）**不控制该事件**，实测无效。

### 1.2 SSP 请求里的 Status（实测分布）

| Status | 含义 |
|---|---|
| `talking,...` | 对话进行中（文字还在显示/播出） |
| `choosing,...` | **选择肢/菜单等待中** |
| `passive,...` | **小游戏进行中** |
| `balloon(...)` / 无 | 空闲 |

### 1.3 小游戏窗体（都是 DLL 自己创建的 Delphi 窗体，不是 SSP 的框）

| 类名 | 用途 | 关闭行为 |
|---|---|---|
| `Ttypinggameform`（含子窗 `TEdit`） | 打字游戏的输入框 | `FormCloseQuery`(需 [Self+0x321] 已提交) → `FormClose`=caFree（销毁） |
| `Teyesightform` | 问答第一题的 C 图窗；视力检查共用 | `FormCloseQuery` 无拦截（0x4704EC 直接 ret）；`FormClose`=caFree（0x470544） |
| `Tcountdownform` | 倒计时显示窗（FormCreate 0x46F104 / FormPaint 0x46F284 / timerTimer 0x46F488） | 无 `FormClose` → 关闭=**隐藏(caHide)**，可复用 |

## 2. 双击判定（桩B：`.cave+0x500`，挂 0x4782BD）

按优先级：

1. 请求含 `"Status: choosing"`（选择肢/菜单等待中）→ **吞掉**（清响应跳 0x478848，SSP 收 204）。
   配合 SSP 设置「左双击 = 不执行任何操作」即完全无反应。
2. 请求含 `passive`（小游戏进行中）：
   - `EYEBUSY`=1（**视力题目已弹出：C 图窗+输入框都在**）→ 吞掉（答题中防误触退出）；
   - `MARK`=1 且 `EYEBUSY`=0（视力已进入但还没弹框）→ 置 **PENDING**（桩A 会给本次
     响应前置含 `\![leave,passivemode]` 的 CLOSE_CMD）+ 调关窗小段（防 C 图窗已在的
     竞态）+ 清响应后跳原版入口 0x4782C5 出主菜单。原版该入口依赖请求里的鼠标
     Reference（只有真实双击事件才带），照此走才会出单，同时被动模式被一并退掉；
   - `MARK`=0（打字/问答）→ 菜单缓存（cave+0x960）非空则 LStrAsg 写回缓存菜单
     （SSP 显示该游戏那层菜单，便于点「退出」）；缓存为空 → 吞掉。
3. 输入框标志 `FLAG`=1（搜索/问答等 SSP 输入框打开）→ 吞掉。
4. 其余 → 清响应后跳 0x4782C5，走 ghost 原逻辑（弹主菜单）。

注意：**不要**在拦截出口动 DLL 内部"点击/菜单状态机"字节 0x4B29E8——它在
菜单流程里有自己的状态转移，清零会破坏"菜单→开始"流程（曾导致点 Period 进不去）。
只在打字框弹出（`OnOpenTypingbox`）时兜底清零，保证答题发送可用（见 3.2）。

实现要点：

- 请求扫描约定：**[ebp+8]=请求字符串指针（PChar）、[ebp+0xC]=指向长度的指针（DWORD\*）**
  （经 0x45F220 与 `System.Move`(0x40283C：EAX=源/EDX=目的/ECX=字节数) 联合反汇编确认）。
- 命中"吞掉" → 清响应（[ebp-0x1c]）后跳公共出口 0x478848（SSP 收 204）。
- 标志/缓存都在游戏状态区（由桩A 维护）：见第 3、5 节。

## 3. 状态维护与响应监控（桩A：`.cave+0x600`，挂 0x47A399）

挂在事件响应汇总点（所有响应都经过；request() 帧内，EBP 有效）。
读**事件名**（[ebp-0x4c]），按前缀分流：

| 事件名前缀 | 动作 |
|---|---|
| `OnUs`\*（OnUserInput 取消输入框） | `EYEBUSY`=1（视力输入框被取消）→ 按**空提交**处理（见 4.3）；否则 FLAG=0 |
| `OnGo`\*（OnGoogle 搜索提交） | FLAG=0 |
| `OnQu`\* | `OnQuizLeave` → 置 PENDING+GAMELEFT+关窗体；`OnQuizEnter` → 清 GAMELEFT；其余（进度事件）→ 见 GAMELEFT |
| `OnTy`\* | `OnTypinggameLeave` → 同上；`OnTypinggameEnter` → 清 GAMELEFT；其余 → 见 GAMELEFT |
| `OnEy`\*（视力） | 取事件名第 15 字符起（[esi+14]）分流：`Next` → FLAG=0、MARK=1、EYEBUSY=1（题目弹出）；`Inpu` → FLAG=0、MARK=0、EYEBUSY=0（本局结束）；其余（Enter 等）→ FLAG=0、MARK=1、EYEBUSY=0（已进入未弹框） |
| `OnOp`\*（OnOpenTypingbox） | **状态机字节 0x4B29E8 复位为 0**（见 3.2） |

其余固定动作（每次响应都跑）：

- **PENDING**（cave+0x948，退出事件/视力未弹框双击时置 1）：把 `CLOSE_CMD` 前置到
  本次响应最前面（仅一次）：
  `\![quicksection,false]\![close,communicatebox]\![close,teachbox]\![close,inputbox,__SYSTEM_ALL_INPUT__]\![leave,passivemode]`
  （关闭 SSP 侧输入框并退被动；问答/打字退出时 DLL 自身响应本来就以 `leave,passivemode`
  开头，属等价冗余；打字框是 DLL 自己的窗体，不靠这些命令，多关无副作用）
- **GAMELEFT + SWALLOW**（cave+0x94C / 0x94D）：游戏已退出期间，游戏自己的进度事件
  （提交/下一题/超时）响应整条清空（204），断掉游戏链，避免残留事件继续出新题；
  重新进入游戏时（Enter 事件）清 GAMELEFT。
- **菜单缓存扫描**：响应里含 `\![*]\q[`（菜单脚本）→ 整条复制到缓存
  （cave+0x960，上限 0x6FC），供双击重放。
- **输入框标志扫描**：响应里含 `\![open,inputbox` → FLAG=1。
- 最后复刻被覆盖的 `cmp/jne` 指令并跳回原路径（0x47A3B1 / 0x47A39F）。

### 3.2 踩坑记录：缓存头压到标志位 & 测试环境里的老 materia

**坑一：缓存头（refcount）压到 GAMELEFT。** 菜单缓存（cave+0x960）的
Delphi 字符串头是 `[refcount][len][data]`，refcount 写在缓存偏移 −4 处。
把数据区往右搬时必须给它留出这 4 字节空隙，否则每次写缓存都会把相邻的
标志字节（GAMELEFT/SWALLOW 等）覆盖成 `0xFFFFFFFF` → "游戏已退出"被误判 →
**所有游戏进度事件（Start/Next/Input）响应被吞** → 表现像"打字游戏点 Period
进不去/答完不跳下一题"。教训：**搬数据区后必须做区间重叠检查**（布局表见第 5 节，
已校验无重叠）。

**坑二：测试时同时开着老的 materia.exe。** 老 MATERIA 也监听/占用 SSTP，
会截走 DLL 通过 SSTP 发出的 `\![raise,OnTypinggameInput,...]`（表现为 SSP 里
冒出一个显示该脚本文字的气泡、游戏不推进）。**测试前务必确认没有其它
MATERIA/SSTP 程序在运行**（关掉 materia.exe 后重启 SSP 即恢复正常）。

> 附注：DLL 的发送函数 `0x4ABC34` 开头有 `cmp byte [0x4B29E8],0; jne ret`
> （该字节是原版双击/菜单状态机的状态，非 0 时静默跳过发送）。我们曾在
> 双击拦截出口 / 盒子弹出时清零它，均被证实会干扰菜单流程，**已全部移除**，
> 不要再去动这个字节。

### 3.1 坑：事件名 [ebp-0x4c] 必须装 SEH

对没有 ID 的请求（SSP 启动时的协议探测 `GET Version SHIORI/2.6` 等），
[ebp-0x4c] 是**未初始化的栈残留**，可能是小整数 → 直接解引用即崩；
Delphi 捕获异常后探测响应变 NULL/500，SSP 便降级为 SHIORI/2.2（该 ghost 只认 3.0），
所有事件都回 500、ghost 无法启动。

现在这段读取装了 SEH 保护：一旦异常，处理器把 Eip 改到收尾处，安全跳过事件名判定。

## 4. 小游戏退出流程（打字/问答一起处理）

### 4.1 流程

点击「退出」→ SSP 发 `OnQuizLeave` / `OnTypinggameLeave` → 桩A：

1. PENDING=1、GAMELEFT=1；
2. 调**辅助桩**（`.cave+0x400`）：按类名 `FindWindowA` 依次找
   `Ttypinggameform`、`Teyesightform`、`Tcountdownform`，找到就各发一条
   `WM_CLOSE`（异步 PostMessage，不会死锁）；
3. 本次（退出）响应前置 CLOSE_CMD → SSP 关闭输入框并正常播放 goodbye
   （`\![leave,passivemode]` 完整执行）。

### 4.2 为什么用 WM_CLOSE 而不是模拟回车

最初尝试模拟回车（WM_KEYDOWN/CHAR）关打字框，发现两个问题：

1. **raise 打断 goodbye**：打字框的 `editKeyDown`（0x46EAEC）在回车时会向 SSP 发
   `\![raise,OnTypinggameInput]`；SSP 处理 raise 事件会取消正在执行的
   `\![leave,passivemode]` → passive 不退、双击又进游戏。
2. **提示音**：单行编辑框对未消费的回车会 MessageBeep（"叮"）；
   DLL 自己的超时关闭走 Close 路径，所以它是安静的。

改成 WM_CLOSE 后走 DLL 的 Close 路径（与超时相同），既没有 raise 也没有键盘消息，
两个问题一起消失。

### 4.3 视力输入框被取消（关闭）→ 按空提交处理

用户关闭 SSP 输入框时 SSP 发 `OnUserInputCancel`（Ref0=OnEyesightgameInput）。
原版 DLL 回 204（materia 时代输入框无法关闭，它没处理）→ 输入框没了、答题期
双击又被禁用 → 卡死。桩A 在 `EYEBUSY=1` 时把响应改为
`\![raise,OnEyesightgameInput,]`：SSP 触发该事件（空值），DLL 走和超时/空输入
**完全一样**的收尾（反馈 + `\![leave,passivemode]` + 关视力窗）。

### 4.4 CloseQuery 放行桩（`.cave+0x10D0`，挂 0x46EE00）

`Ttypinggameform.FormCloseQuery` 原本是 `CanClose := [Self+0x321]`
（只有回车提交/超时才置位），辅助桩发 WM_CLOSE 时该标志为 0 → 会被拒绝关闭。
放行桩在 **GAMELEFT=1** 时直接 `CanClose=1`，其余情况保持原逻辑。
（`Teyesightform` / `Tcountdownform` 无此限制，不需要桩。）

### 4.5 结果

- 打字游戏退出：输入框立即关、无"叮"、goodbye 完整、passive 正常退；
- 问答退出：SSP 输入框 + C 图窗（`Teyesightform`）一起关；
- 倒计时窗（`Tcountdownform`）关闭（隐藏），与"回复后消失"行为一致。

## 5. `.cave` 布局（菜单/游戏部分）

| 节内偏移 | 内容 | 大小/说明 |
|---|---|---|
| 0x110 | 类名 `Ttypinggameform\0` | |
| 0x120 | 类名 `Teyesightform\0` | |
| 0x130 | 类名 `Tcountdownform\0` | |
| 0x140 | 空提交脚本 `\![raise,OnEyesightgameInput,]`（dstr，数据@0x148） | |
| 0x380 | 视力未弹框双击小段（自设 ebx → 调关窗辅助桩） | 20 字节 |
| 0x400 | 辅助桩：FindWindowA×3 + WM_CLOSE×3 | 0x400-0x486 |
| 0x500 | 桩B：双击判定 | ≤0x100（当前 0xFD） |
| 0x600 | 桩A：状态维护/响应监控 | 0x311 |
| 0x940 | FLAG（dword） | 输入框标志 |
| 0x944 | MARK（dword） | 视力游戏标记 |
| 0x948 | PENDING（byte） | 本次响应前置 CLOSE_CMD（仅一次） |
| 0x94C | GAMELEFT（byte） | 游戏已退出 |
| 0x94D | SWALLOW（byte） | 本次响应待吞 |
| 0x94E | EYEBUSY（byte） | 视力输入框已弹出 |
| 0x95C / 0x960 / 0x964 | 游戏菜单缓存（rc / 长度 / 数据） | 上限 0x6FC |
| 0x1050 | CLOSE_CMD 常量 | 124 字节 |
| 0x10D0 | CloseQuery 放行桩 | 28 字节 |
| 0x10F8 / 0x10FC / 0x1100 | PENDING 前置拼接缓冲（rc / 长度 / 数据） | 数据上限 0xE00 |

- 节属性：CODE|EXECUTE|READ|WRITE；追加在文件末尾（RVA 0xE2000）。
- 所有桩为**位置无关代码**（相对跳转/调用 + call/pop 自定位取址）。
  **不要写构造期绝对地址**：SSP 自己占着首选基址 0x400000，
  first.dll 每次都会被重定位（实测加载在 0x0BBD0000 附近）。
- 其余偏移（0x000/0x020/0x100/0x1F8 等）为链接补丁用，见《链接机制说明及补丁.md》。

## 7. 实测教训（踩过的坑）

- **同步调用会死锁**：不要在响应处理里同步调 DLL 的提交处理函数；必须 PostMessage 异步。
- **重定位**：模块实际基址不是 0x400000（见第 5 节）；绝对地址读写会读到别的内存
  （曾导致"所有回车都被当成退出拦掉"）。
- **不要写 [ecx]**：`editKeyDown` 在字符串构造调用之后 ecx 已被破坏，
  写它触发异常且 Delphi 异常派发器二次崩溃（STACKTRC 0x403AF2 的 rep movsd 空指针）。
- **[ebp-0x4c] 未初始化**：见 3.1。
- 改动 DLL 数据布局后，所有相对偏移（如桩B 读缓存的 [eax+0x10]/[eax+0x14]）要同步更新。
- **别让桩超出自己的槽位**：桩B 超过 0x100 会覆盖到 0x600 的桩A 首字节
  （曾把 `push eax` 盖成 `FF`，表现为"进入游戏直接回车崩溃"的前科）。
  构建时都有长度断言。
- **辅助桩（0x400）的接口约定**：以 ebx=cave+0x60B 为基址且不恢复 ebx。
  调用方需自设/恢复 ebx——桩A 天然满足；桩B 经 .cave+0x380 小段调用。
  辅助桩实际占 0x400-0x486，新代码别放进这一段。

## 8. 窗口文本编码（DFM Font.Charset → GB2312_CHARSET）

DLL 是 ANSI 程序，DFM 字符串按字节交给系统，按渲染路径分两种解释：

- **TLabel 等 VCL 自绘文字**：GDI 的 ANSI 文本函数按**当前字体 charset 对应的代码页**
  转换字节；
- **窗口控件（TButton / TCheckBox / TTabSheet / TTreeView / TEdit 等，有 HWND）**：
  文案走窗口消息，系统按 **ACP**（本机 = 936/GBK）转换。

原版把 18/20 个窗体的 `Font.Charset` 设为 `SHIFTJIS_CHARSET`（CP932），所以这些窗体里的
TLabel 文案必须是 Shift-JIS——`translated.csv` 中原先有 12 条 rsrc 行（Tfirstconfigform /
Tnotifyform 的全部 label：うるさい ／ 黙 ／ 月 ／ 日／毎週 ／ 時 ／ 分 ／ メッセージ ／
日時 ／ 実行ファイル ／ 年 ／ 曜日 ／ 喋る頻度(&A)）靠 `SHIFTJIS_OFFSETS` 特判保持 SJIS，
译文只能用 SJIS 允许的字符。唯一未设 charset 的 Tversionforms，其 label（beveltitlelabel）
本来就按 ACP 走，GBK 无碍。

现由 `patch_dll.py` 的 `patch_dfm_charset()` 把这两个窗体的 `Font.Charset` 改为
`GB2312_CHARSET`（值编码 `07 10 "SHIFTJIS_CHARSET"` → `07 0E "GB2312_CHARSET"`；
值之后到本窗体数据块末尾的内容整体左移 2 字节、块尾补 0，资源大小与后续资源位置不变；
**必须在文本翻译写入之后执行**，翻译随区块一起平移、DFM 结构保持自洽）。改后这两个
窗体的 label 文案按 CP936 解释，随大流使用 GBK；`SHIFTJIS_OFFSETS` 已清空，那 12 行
译文可改用任意 GBK 汉字。其余 16 个窗体保持 `SHIFTJIS_CHARSET` 不变（其中没有
需要翻译的 label 文案）。
